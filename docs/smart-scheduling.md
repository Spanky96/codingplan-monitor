# 智能调度与人工分类

智能调度由监控端规划、中转站执行。初始关闭。管理员选择参与账号并启动后执行。按量付费和备用分流也默认关闭。监控端与 `lwsub2api` 需要一起升级。

## 操作方式

未参与账号继续沿用原权重策略。个人账号若只需监控，可将原权重设为 0；想贡献富余额度时，可手动开放权重，或勾选参与并选择低速保护。

管理员右上角进入「智能调度」。勾选参与账号，设定用途、调度模式、总并发上限、容量系数和自动用卡权限，然后保存并启动。

| 分类 / 模式 | 行为 |
|---|---|
| 自动决策 | 按周和 5h 额度分流，富余账号可追赶进度，允许用卡的账号可接力承担流量 |
| 低速保护 | 人工将目标流量降低至常规计算的 20%，并发降至每关联渠道 1；不代表固定 RPS |
| 手动高速 | 人工提高目标流量至常规计算的 4 倍，仍受额度、限流和并发上限限制；不自动撤销人工模式 |
| 已耗尽 | 真实额度决定，权重立即为零，不能用固定权重或主动模式强行复活 |
| 按量付费 | 独立授权开关。无余额接口的占位账号须另外勾选「允许无余额数据的按量占位」 |
| 其他模型 | 原生渠道正常参与，备用渠道单独按授权和主力余量开启；不绑定 MiniMax 品牌 |

默认保留全部账号通铺及原账号顺序，卡片标明托管模式和当前状态。管理员可在工具栏开启「调度分类」，此时显示调度摘要、分类筛选和分组标题，每类内部按计划优先顺序排列；权重、紧张度、调度量排序作用于各分类内部。再次关闭即回到通铺，分类筛选同步清除，视图选择保存在当前浏览器。视图切换不改变线上调度策略。点击已托管账号的权重直接进入调度控制台，不再修改会被自动覆盖的固定值。

主页面的付费 / 备用分流状态读取中转站实际可调度状态，并包含已知但未托管的同类账号；没有新鲜快照时显示「未检测」。是否已执行还要看「中转站确认」，计划生成不等于执行成功。分类标题中的开启数指目标权重。

移除了「需要重置」徽章。悬浮右上角状态可见预计不可用时长；多个窗口耗尽时取**最晚恢复时间**，缺少官方时间时不编造倒计时。未耗尽账号的提前耗尽信息标明为预测。

## 额度与并发算法

这是一套可解释、确定性的控制器，不通过大模型决定是否扣卡。

1. 每 30 秒重新规划；所选账号用量约每 60 秒后台刷新，最多两个上游查询并行。无需浏览器常开。
2. 均衡及余量追赶的周目标消耗速率为 `剩余周百分比 / 距自然重置小时数`。相对于完整周的平均速率 `100 / 168` 归一化并开平方，避免临近重置时权重无限放大。已授权且库存有效的**周卡衔接高速**，目标是耗尽当前周额度后补充，因此在加速有效且没有短窗口保护时，周因子至少为 1，再乘高速系数；不会把最后几个百分点继续摊到旧的自然恢复时间而抵消加速。计划的 `weeklyWeightFactor` 和原因说明可用于核对。短窗口保护、限流或用卡条件失效时恢复原周节奏计算；周额度 100% 耗尽仍立即停流，是否用卡另行复核。
3. 5h 因子为 `(剩余百分比 / 距重置小时数) / 20`，限制在 `0.05–2`。短窗口紧张会降低分流，临近短窗口重置且仍有余量则加速消耗。
4. 乘以套餐容量系数。官方各版本的计量单位不同，不把 CREDIT 与 TOKENS 当作相同绝对额度；同档套餐保持 1，不同档通过此系数表达相对容量。
5. 人工低速 / 高速模式作用于目标比例。普通变化按 65% 旧权重 + 35% 新权重平滑；耗尽、数据失效、暂停、兜底关闭立即生效，不平滑拖延。
6. 并发与权重分开控制。智谱主力池总并发以 4 为安全上界，同时尊重更低的人工上限。正常从 2 开始，进入高速且有需求、短窗口充足、无近期限流时试探增加 1。连续有效采样达到实际执行容量的 75% 并持续两分钟后再增加 1。采样中断超过 90 秒、闲置或限流会重置繁忙计时；不以尚未执行的容量作为繁忙分母。上游限流时减半，恢复观察两分钟。下调只限制新请求，不打断在途流。
7. 同一监控账号对应多个中转渠道时，权重和并发按**账号总预算**拆分，不给每个副本重复一份额度。仅在实际开放的渠道中分配，原生渠道优先，再按 ID 稳定分配；未确认的新渠道暂停，预算不足时额外渠道暂停。通常把上限至少设为渠道数。
8. 观察连续官方额度样本，以 EWMA 估计 5h / 周消耗速率。至少三个有效增量样本后，若预计 45 分钟内耗尽且自然恢复还超过一小时，提前进入短窗口保护；预计不足 15 分钟且恢复超过 45 分钟则加强保护。官方重置时间的小幅毫秒漂移不清空历史，真实新窗口、用量下降或样本中断超过十分钟会清空速率。
9. 轻微短窗口节奏偏差只调整权重，不再用 `floor(并发 × sqrt(因子))` 直接减半。节奏因子低于 0.6（或短窗口用量达到 85% 且恢复还需半小时）限制至 2；低于 0.25（或达到 95% 且恢复还需半小时）限制至 1。退出保护使用更高阈值 0.75 / 0.4，减少来回切换。

每个工作日的周预算为 20 个百分点，对应卡片上的一格。调度检查有直接渠道、额度数据新鲜的托管主力。当至少两个账号比各自的工作时间理论水位领先一格，有近期需求时，会提前选择一个有周卡的主力承担更多流量。候选账号可以低于 50% 周用量。试算按该账号本周平均速度的两倍估计耗尽时刻，保留至少 24 小时的用卡收益。V3 两个窗口有同单位总额时，耗尽时刻还要考虑当前 5h 余额能否支撑。该速度是分流假设，实际供给取决于负载和短窗口。

单账号仍可凭自身进度触发高速。进入条件为周用量达到 50%、领先自然时间进度至少 15 个百分点、按本周平均速度预计比自然恢复早至少 24 小时耗尽。两条路径共用需求、15 分钟内核实的有效周卡、卡的有效期、预计补充时间、5h 保护和上游限流检查。每轮最多选一个周卡自动高速账号。优先选能立即承接流量且周用量较高的账号，上一轮接力者有 5 个百分点的排序余量，减少频繁切换。接力生效时，超前一格的其他自动均衡账号目标权重减半，保留并发和服务能力。手动模式及周额度富余追赶仍独立计算。

V2 与 V3 都以官方 usage 为准，不把百分比当 Token，不重复施加高低峰计费倍率。只有官方同时返回同单位 `CREDIT_LIMIT` 总额时才联动两个窗口：例如 28000 / 140000 表示一轮完整 5h 额度相当于 20% 周额度。只有百分比的账号分别估计各窗口，不猜换算比例。官方已核算的实际消耗速度用于高峰时的提前保护；套餐间绝对 Token 供给不作未经验证的比较。

现有中转站的显式权重路径会绕过部分优先级 / Top-K 筛选；会话粘性、模型支持、分组路由、并发槽位、上游冷却仍然生效。因此界面的「目标份额」是所选池的新请求目标比例，**不是严格保证的 Token 百分比**。优先级字段主要用于展示顺序，实际分流由权重和真实并发槽位执行。总需求高于总供给时，不能靠排序保证全天不断供。

## 今日用量和 18 点前可用 Token

周条五格各占 20%。白色斜纹表示当天起点之前累计使用的额度，实色表示当天起点至本次官方读数的增量，实色上叠加白色高光循环扫过（「充电中」观感，`prefers-reduced-motion` 时关闭）。悬浮或键盘聚焦可查看起点、终点、采样时间及格数。列表视图的周环用内圈细线标出同一区间。服务在北京时间零点后台拉取智谱周额度，和其他用量请求共用在途查询。起点随用量缓存落盘，独立于账号列表的排序。缺少零点读数时标明当天首个读数的时间。日内开始新周窗口后从零标出本轮用量。

调度分类摘要每天北京时间 18:00 前显示「18:00 前预计可用 Token」。服务每两分钟读取一份中转 Token 汇总，和实际官方 5h、周用量配对。采用最近一小时内至少间隔五分钟且有明确额度变化的样本。V2 分别标定两个窗口。5h 变化至少两个百分点时才采用样本，周变化小于两个百分点时在观察增量上加一个百分点，保守处理整数读数的取整误差。V3 可利用同单位积分总额的比例。样本不足时可参考至少两个同版本、同档、同配额类型账号的中位数。按近期吞吐推算到截止时间，每段取吞吐、短窗余量和周余量三者中的最小值，并按各自时间计入自然恢复。待使用的卡不计入供给。统计包含未托管的 Coding Plan，排除按量占位及其他平台。覆盖不全时显示已测账号数，悬浮可查看参考同档的数量。模型组合、峰段和实际请求速度变化都会影响估算。

## 有限重置卡的决策

勾选「不使用重置卡」后，调度和详情页手动用卡都会被阻止。新加入的个人 Coding Plan 主力默认未勾选。既有账号沿用原权限，原来允许用卡的显示未勾选，原来未允许的显示已勾选。管理员在调度控制台取消勾选并保存后，该账号可参与周卡接力。自动决策和手动高速仅在对应窗口实际耗尽、上游用量可信、中转站已确认接管时自动提交。低速模式暂缓自动用卡。每次提交前复查官方库存、额度、最新权限和中转站负载。

必须同时满足：

- 对应窗口确实耗尽（100%）；有 CREDIT 实际数值时同时核对已用量达到总量、剩余量为 0，避免百分比四舍五入误判。周卡只解决周窗口，5h 卡只解决短窗口。
- 周窗口距离自然恢复 **至少 24 小时**；5h 窗口距离自然恢复 **超过 1 小时**。因此「还有半天自然重置」不会自动用周卡。
- 若配置了「预计充值 / 额度补充完成」，也会等待即将到账的额度。
- 使用周卡后不能仍被长时间耗尽的 5h 窗口堵住。存在同单位官方总额时，若剩余周额度只能消化不到一张 5h 卡的 25%，不用短卡；缺少可比总额时保留“周用量超过 85% 不用短卡”的保守判断。
- 自动决策模式近期无主力请求时先等待需求；手动高速的明确衔接意图保持原语义。

不再设置每日张数、卡片保留量或全局十分钟冷却；有其他账号余量也不阻止已明确授权的高速账号衔接。

同账号同类型优先使用最早到期卡；多个账号同时适合重置时，比较自然恢复距离与卡片临期因素，每轮只重置一个，再重新观察。没有 5h 卡就不会假设存在，也不会用周卡代替。

卡列表没有提供未来补发或充值到账承诺，所以**未来补充时间须由管理员填写**。这不是充值接口，不会自动购买卡或充值。

提交前持久化账号、卡类型、recordId、requestId；网络超时或进程重启后不自动重复提交同一张卡。官方明确拒绝时保留原额度状态；结果不确定时账号进入待验证状态。观察到用量确实下降 / 窗口改变并恢复后，立即通知中转站拉取新计划，恢复权重和调度；只清理验证时间之前的限流冷却，不解除鉴权错误、手动状态或临时封禁。

自动核对无法确认的用卡结果需要管理员在官方控制台核实。`scheduler-state.json` 的 `journal` 保留完整去重记录，不应通过删除整个文件来重试。

## 兜底

按量与备用分流分别授权。默认在主力全部不可用时兜底。选择「主力额度紧张时，小比例分流」且近期有主力需求时，调度还检查以下条件。

- 至少两个主力且占有效额度样本的三分之一达到风险条件，持续一分钟后，以主力总权重的 15% 为分流目标。一个账号只计一次。周窗风险要求距自然恢复至少 24 小时，同时领先工作时间水位至少 20 个百分点，或周用量已达 90% 且领先至少 10 个百分点。正在执行周卡高速的账号按计划超前，仍检查其短窗风险。短窗风险要求已用至少 85%、处于短窗保护或短窗已耗尽，且距恢复超过 45 分钟。额度已耗尽、等待恢复的账号可计入样本。
- 所有可用主力的短窗已用至少 85% 或周用量已达 95% 时，立即采用 15% 的预防预算。持续一分钟达到主力并发容量的 85% 时采用 10%。未来 45 分钟预计有至少 40% 的并发面临耗尽，且需求达到预计最低容量的 75% 时，持续一分钟后采用 5%。多个条件取较高预算。
- 压力消退后保留三分钟观察。预防性额度分流有至少两个补充槽位、两类均获授权且备用有余量时，至少留一个槽位给备用。实际需求超过主力容量时，按并发缺口增配按量和备用。权重影响新请求，实际分流量受模型路由与会话粘性影响。

每个配额账号下的中转渠道按稳定 ID 设置「直接调用 / 备用分流 / 暂停」。关闭备用分流只停止对应渠道，原生渠道继续工作；额度耗尽时全部渠道停止。原生与备用共享账号总权重、总并发预算，不会重复分配一份。

例如 MiniMax1 的 81、82 渠道可设为直接调用，104（GLM → MiniMax）设为备用分流。其他模型也适用。界面建议只根据已有模型映射生成，管理员可覆盖；一个中转渠道内若同时混合两种用途，应先拆成独立渠道再分类。

## 接入与部署

1. 备份服务器两项目当前版本、监控 `accounts.json` / 用量缓存以及中转站数据库。发布代码时保留线上数据，不要覆盖成开发机账号。
2. 先构建并部署支持智能调度协议 v2 的 `lwsub2api`。它支持旧权重格式，监控尚未升级时仍可用。无需数据库迁移，新元数据在已有 `extra` 中保存。
3. 在两服务运行环境配置相同随机 `SCHEDULER_SYNC_TOKEN`。中转站四份 Compose 模板已传递该变量，留空则即时写入口拒绝请求。
4. 监控配置 `SUB2API_BASE_URL=https://lwai.05info.com:8887`，或能够从容器访问的中转站内部 HTTP 端口。实测 `http://192.168.0.20:8887` 会返回「HTTP 请求发送到了 HTTPS 端口」，不能用于本配置。
5. 中转站开启原有权重同步，地址设为 `http://192.168.0.20:8886/api/weights?password=<URL 编码后的监控管理密码>`，轮询间隔建议 30 秒。服务自动追加 `schedule=1`。即时同步还会校验源标识，避免误连另一套监控。
6. 部署监控。Compose 已持久化 `/app/data/accounts.json`、`usage-cache.json` 和同目录 `scheduler-state.json`。其他部署方式通过 `ACCOUNTS_FILE` / `USAGE_CACHE_FILE` / `SCHEDULER_STATE_FILE` 指定持久化目录。
7. 管理员打开控制台，核对渠道匹配数量和当前并发，选择账号与模式。在需要保卡的账号勾选「不使用重置卡」，保存后核对计划与中转站确认。

该控制器面向当前**单实例监控服务**；不要让多个监控进程同时写同一状态文件或管理同一批账号。中转站同步已有进程互斥及 Redis / 数据库领导锁。

## 停止、故障与回滚

- 「停止托管」立即通知中转站恢复托管前的并发、负载因子、优先级；权重恢复当前原有策略，已耗尽账号仍保持 0。未选择账号始终沿用原有策略。
- 每个托管账号携带 180 秒执行租约；计划过期、数据超过 10 分钟或缺失时输出 0。控制器失联后租约到期停止新调度，覆盖粘性路径，不让付费 / 备用分流永久遗留开启。
- 上述策略选择在控制器失联时停止托管池的新流量，而非自动启用付费兜底，可能影响可用性；界面会显示待同步或数据过期。
- 回滚前先停止托管并确认中转站已恢复配置，再回滚两服务。不要先回滚中转站而让监控继续输出托管计划。

## 验证

监控执行 `npm test`。中转站在 `backend` 执行：

```sh
go test ./internal/service ./internal/repository ./internal/handler/admin -run 'Test(MatchWeight|PickAccount.*Weight|SelectFromEligible|Smart|DecodeWeight)' -count=1
```

测试覆盖耗尽 / 过期不复活、周/5h 独立用卡、半天自然恢复不用周卡、自动高速进入/退出、独立用卡授权及提交前撤销、无每日/保留量限制、百分比取整保护、并发安全上界和持续繁忙/限流恢复、V2/V3 官方口径、原生/备用渠道独立控制、近期充值、重复提交、失联租约、关联渠道总预算、配置恢复以及模型扩展配色。线上启用时经用户明确授权，glm8 与 glm12 各自动使用一张周卡并验证恢复；后续回归使用隔离模拟，不为测试额外消耗卡。
